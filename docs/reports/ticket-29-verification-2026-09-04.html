Indexing changes made outside the app

#29's acceptance criteria are all about behaviour in the running application: a note edited by another program, a folder deleted behind the app's back, a sync burst. A unit test can call the indexing code directly and pass while the real path is broken — which is exactly what happened here once. Every criterion below was therefore also driven against the built release binary.

All acceptance criteria pass against target/release/helixnotes. One real defect was found by doing this rather than trusting the suite; see the defect the unit tests missed.
Branch feat/29-index-external-changes Linux / Wayland pnpm verify green — 254 Rust tests

Method

The app cannot be queried from a script, so each run: seeds a vault and points the app's config at it; starts the release binary and lets it finish its startup rebuild; makes the changes entirely from the shell, never through the UI; waits past the 400 ms settle window; SIGKILLs the app so nothing is flushed on a clean exit; then opens the index the watcher left behind from a separate process and queries it.

The kill matters. The app rebuilds the whole index when a vault opens, so a run that ended cleanly and reopened would show a correct index no matter what the watcher did. Reading the index the killed app left is what makes the result evidence about the watcher.

The defect the unit tests missed

“A note deleted outside the app disappears from search results”

A unit test covered deleting a folder and passed. It called the indexing function directly, so it never went through the watcher — and the watcher was discarding the event before the indexer could see it: 

let has_md = event.paths.iter().any(|p| {
    p.extension().and_then(|x| x.to_str()) == Some("md") || p.is_dir()
});
if !has_md { continue; }

Once a folder is gone it no longer reports as a directory, and a folder never had a .md extension. So a notebook moved out of the vault matched neither test and was dropped. Measured against the real app before the fix: 0 notes on disk, 5 still in the index — results pointing at files that no longer existed.

The fix gives the indexer its own, laxer rule (should_index): forward notes so they can be read, and forward anything that no longer exists so it can be removed, because a vanished path may be a note or a folder full of them and the event cannot say which. An existing non-note is still withheld, since indexing reads files as text and an image would fail the whole batch.

Second spec review — two more findings

The first spec-axis review died on a rate limit and was done by hand instead. It was re-run properly against the fixed commit, and found two things the manual pass missed. Both are recorded here because both were real.

The watcher and the rebuild disagreed about what a note is

“Index updates survive an app restart — no stale entries left behind by changes made while the app was closed.”

rebuild() prunes every dot-prefixed entry; the watcher's filter excluded only .helixnotes. So a hidden note such as Projects/.draft.md created outside the app became searchable immediately and then silently disappeared at the next open — the index depending on which route last touched it. Not a stale entry, so it read as a partial rather than a failure, which is precisely why it was easy to miss.

Fixed at the root rather than by patching one side: both now consult one is_ignored_by_index, so they cannot drift again. Measured against the running app with a hidden note and an ordinary one created together: 1 indexed before restart, 1 after — nothing appearing or vanishing.

Removals scanned the index once per path

“A burst of many external changes coalesces rather than reindexing per event”

Resolving a vanished path meant a full scan of the stored index values, and that ran once per removed path. A sync burst deleting a thousand files would have done a thousand full scans inside a single flush. The batch was still one commit and the work sat on the indexer thread, so the UI stayed responsive — but the scan was per path, not per batch. Now one pass matches every removed directory in the batch. Verified with three notebooks deleted at once: 5 notes left on disk, 5 in the index.

Worth stating plainly: the manual spec pass found the folder bug but missed both of these. Re-running the agent was the user's call, and it was the right one.

What this does not cover

  • Windows. Not run — no machine available, same gate as #27's V5. notify reports renames differently there, which is precisely the area this ticket depends on, so the folder cases above are worth repeating on Windows.
  • “The UI stays responsive throughout.” Verified only as “the process survived and indexed all 2000 notes”. Frame timing during a burst was not measured.
  • A file appended to forever (a log-like file that never stops changing) is held back indefinitely by design and so is never indexed. Correct for notes; recorded here because it is a deliberate consequence rather than an oversight.
