Issue #14 — backups only before incoming changes

2026-09-29. The second of two #14 pull requests. Until now every sync batch took a full pre-sync backup, every five minutes on both machines, whether or not anything arrived. Pruning kept the newest backup_max_count archives from one shared pool, so with sync on, every scheduled backup was gone within about 25 minutes. Nicolas chose to back up only when a batch actually brings changes, and asked for delayed indexes to be handled. This report records the design evidence, the change, and its verification. The first pull request is recorded in its own report.

Spike: what a send-only folder does

A paused Syncthing folder exchanges no index, so the app cannot learn about incoming changes before it resumes. Syncthing's documentation says a sendonly folder still receives changes from other devices, so it can go out of sync, but applies none of them. Two disposable Syncthing 2.1.5 instances on loopback, the version the app bundles, showed:

ObservationResult
Both folders send-only, the peer holding a file this side lacks. The peer's index arrived within 2 s. needTotalItems was 1 and /rest/db/need named the file. In 24 s of watching, nothing was written to the vault.
The peer deletes a file this side has. needDeletes became 1 and the file stayed.
Switch to sendreceive while connected. The file arrived, or the deletion applied, within about 2 s, without a reconnect.
Pause both sides, change the peer, resume both send-only. For about 19 s the local side reported needing nothing: the connection took 18 s to return, and the index arrived 1 s later. During that time remoteSequence still held the previous batch's value. No Syncthing endpoint or event reports that a peer's index has fully arrived.

Change

  • A batch resumes the folder sendonly, type and resume in one change. The first time the folder needs anything, it takes the full pre-sync backup, prunes, and only then switches the folder to sendreceive. The vault is written only after that backup exists. A batch with nothing incoming takes no backup.
  • If the backup fails, the run ends with "Sync aborted because its safety backup failed", the folder still send-only, and nothing received. It reports failure, because the vault is unchanged. Outgoing changes may already have reached the peer, whose own batch backs up before applying them. The same holds for any other error in a run that never took its backup, such as an unreachable peer or a convergence timeout: those runs used to report changed-incomplete, and now report failure, because the folder never left send-only.
  • Delayed indexes: the stability window restarts whenever the peer's remote sequence changes. A send-only device keeps watching what it needs through the 60-second handoff hold, and backs up and receives if anything appears there. Anything later waits for the next batch, and it can never land without a backup.
  • A batch that took no backup skips the projection rebuild, because its folder never left send-only and the vault is as it was.
  • Pausing the folder, at the end of every batch and in the cleanup guard, also returns it to sendonly. Pairing, in the app and in the installed-package harness, configures it send-only.
  • Pruning keeps the newest backup_max_count archives, but always keeps the newest scheduled or manual backup among them, in place of the oldest one that would otherwise stay.
  • The Sync settings hint now reads "A full recovery backup is taken before any incoming changes are applied."
  • The installed sync gate in scripts/alpha-harness.mjs now requires a pre-sync backup on the receiving Windows machine only, and records any on Fedora.

Verification

CheckResult
Live test sync_sidecar::live_tests: two real bundled Syncthing processes on loopback, each batch driven through sync_batch, the function a sync run calls. The backup callback waits 3 s and then records the vault, so any transfer that could land ahead of the backup shows up in the record. Pass, in 360 s:
  • First batch: only the empty side backed up, and its backup saw an empty vault; the note then arrived.
  • Second batch, nothing changed: neither side backed up.
  • Third batch, a note deleted and another added: only the receiving side backed up, its backup still held the deleted note, and afterwards the vault held exactly the new note. The paused folder was send-only again.
  • A late index: the peer's device was reachable but its folder paused, so its index was withheld. After 20 s the vault was unchanged. Once the peer's folder resumed, the batch backed up the vault as it was and then received the new note.
  • A failing backup: the run returned the safety-backup error, the vault was unchanged 5 s later, and the folder was paused and still send-only.
Checked by hand afterwards, not by the test: no Syncthing process and no test folder remained.
An earlier version of the same live test, without the late-index case, with the batch resuming the folder as sendreceive, to show the test detects writing before the backup. Failed as it should: the receiving side's backup recorded note.md already present.
Unit tests: a moving peer index restarts the stability window; a change during the handoff hold ends the hold to be received; pruning keeps the newest scheduled backup among frequent pre-sync ones; the harness pairs the folder send-only. The live test cannot time an index to arrive during the handoff hold itself, so that path is proven by the unit test alone. Pass, with the existing sync and backup tests.

Installed-package follow-up (2026-09-29)

Passed on installed Fedora and Windows packages from 7e67b29. A batch with nothing incoming took no ZIP. Each of six incoming batches per machine took exactly one archive matching the pre-transfer vault; at the UI minimum of 5, pruning kept the manual archive and four newest pre-sync archives. Unwritable backup directories produced the safety-backup-failed message, terminal failure, and no received changes. Both pre-sync restores passed through Settings > Backup.

Maximum archive-write / total-batch times were 0.721 s / 87.441 s on Fedora and 1.235 s / 88.091 s on Windows, for 5,000 notes plus an 8 MiB attachment. All samples passed the 2 s / 120 s budget accepted by the implementing Claude session under Nicolas's delegation.
