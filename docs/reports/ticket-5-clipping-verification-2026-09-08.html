Web clipping from a URL

#5's code merged in PR #43 on 2026-09-07, but the issue stayed open: the PR used Refs #5 rather than a closing keyword, and its own review report listed a live clipping run as the outstanding step. This record is that run — and it found two defects that the fixture-based suite could not.

Method

The earlier suite tested extract_article against HTML fixtures written by the same hand that wrote the parser call, so it could only confirm the author's model of a web page. The two defects below both live in the gap between that model and real sites, and neither fixture could have exposed them.

Verification therefore drives clip_url — validation, DNS pinning, redirects, fetch, and extraction, the whole path the Tauri command calls — against live third-party URLs, as two network-gated tests carrying #[ignore] in the manner already established by hotkey::portal. They are run with cargo test -- --ignored, not in pnpm verify, so an offline or firewalled machine still gets a green suite.

Not covered here: the Svelte click path. This machine is a Wayland session with no xdotool, so the modal cannot be driven from a script. Pasting a URL into the running app and picking a category remains a manual step, listed under what is still unverified.

The two defects the fixtures missed

1. The login-wall heuristic rejected most of the open web

lower.contains("<form") && (… || lower.contains("login"))

extract_article tested for a login wall before attempting extraction, and the test fired when a page contained any <form> element and the string login anywhere in its HTML. That describes an enormous share of the web: a search box in the header and a "Log in" link in the nav is the default shape of a content site.

The user saw "The web page requires login before it can be clipped" for a page requiring no login, so acceptance criterion 1 failed on ordinary input while the suite stayed green. The existing fixture passed because it was a bare login page with no navigation — it never contained the furniture that causes the false positive.

Fix. Readable content decides first. Extraction runs, and a login wall is only ever diagnosed for a page that already produced no article, narrowed to the one signal that is not furniture: an actual password input. A wall is now a better explanation of a failure rather than a gate in front of success.

2. The clipper sent no User-Agent, so Wikipedia returned 403

With the heuristic fixed, the live run still failed — now reporting "The web page requires login or permission before it can be clipped", the 401/403 branch. html_client built a reqwest client with no user_agent, and Wikimedia's User-Agent policy answers an unidentified client with 403.

Fix. The client now identifies the app and where it comes from, which is what those policies ask for. Note that image_proxy.rs omits a User-Agent in the same way; it is out of scope for #5 and is recorded below as a follow-up rather than widened into this change.

A third finding was not a defect. blog.rust-lang.org/…/Rust-1.76.0.html returns a 460-byte JavaScript redirect stub, and the app correctly reported no readable article. The stale URL was in the test, not the code; the canonical trailing-slash URL clips fine. Following meta refresh / scripted redirects is a real gap, recorded as a follow-up rather than fixed here.

Fixed: the vault identity is claimed under an OS lock

vault_id claims the identity file with create_new and writes it immediately after. Those are two steps, so the file is briefly empty — and a process killed inside that window leaves it empty permanently. Every later open then calls read_claimed_vault_id, which polls for 500 ms and gives up, so the vault becomes permanently unopenable. This is what the flaky relocation test is catching: it spawns 40 children killed at 0–78 ms, so it lands in the window every few runs.

The existing code will not take over a stalled claim, and says why: a writer stalled on a slow mount is indistinguishable from a dead one, so replacing the file risks two processes keying one vault to two ids. That reasoning stands. The fix has to remove the ambiguity, not overrule it.

An OS lock is exactly that discriminator, because the kernel releases it when the holder dies.

The creator keeps create_new, so exclusion is untouched, and additionally holds an exclusive lock while it writes. A reader that finds the file empty attempts the lock: if it blocks, a writer is alive and waiting is correct; if it acquires immediately, the previous holder is dead and taking over is safe. Two would-be takers serialise on the same lock, and the loser re-reads the winner's id.

OptionWhy
OS lock (flock / LockFileEx) Chosen Fixes the crash gap while strictly preserving the one-vault-one-id guarantee. No on-disk format change and no migration. flock is VFS-level on Linux, so the FAT/USB constraint that rules out hard_link does not apply.
Put the id in the filename Rejected Removes the empty window but not the race: two processes create two different names and both succeed, so uniqueness weakens from guaranteed to eventually converged. A process could switch ids after building an index keyed to the first. Also needs a format change and a migration.
Age heuristic — "empty for N seconds means abandoned" Rejected Does not fix the observed failure. The test recovers immediately after the kill, so the empty file is always fresh.
Delete the empty file and re-claim Rejected Clean unless a live writer still holds the descriptor — the exact case the wait could not rule out, which is the ambiguity this decision exists to remove.
hard_link for atomic no-clobber creation Rejected Already rejected in-code for FAT/USB portability, and the file lives inside .helixnotes/, so that constraint is real.

Two costs accepted. A new dependency (fs4 or similar, or a small libc/windows-sys wrapper) — worth naming because SPEC §3 made a point of closing the backup gap without one, so this is a norm rather than a free choice. Network filesystems — flock over NFS is historically unreliable; where the lock is a no-op the behaviour degrades to what happens today, which is no worse.

Implemented in 48c3a4e. fs4 is already in the tree via tantivy, so making it a direct dependency adds no crates to the build — which removes most of the dependency objection above.

Two ways this could have made things worse, both handled. A filesystem that cannot lock falls back to the previous conservative behaviour rather than refusing to open the vault at all. And because claiming now opens the marker for writing, a vault on a read-only mount would have stopped opening entirely; an identity already recorded there is read without writing.

One residual risk is worth recording because no number of passing runs can retire it: the test ends with two sampling assertions — interrupted > 0 and restored > 0 — which depend on a kill landing inside a narrow window across the 40 delays. If scheduling ever fails to cooperate, the test fails with nothing wrong in the product. That is a defect in the test rather than the vault, and it is untouched here.
