Manual verification plan

What the suite cannot prove about ticket #27

#27 moved machine-local state out of the vault. Its own text warns that “a green test suite is not evidence here — the recovery code only runs when something was interrupted, which is exactly the case tests tend not to produce.” This is the list of claims the automated suite does not establish, and the procedure for each. It is a gate on merging, not a backlog.

Run 2026-09-04: V1, V2, V3 and V4 pass against the built release binary. V5 (Windows) could not be run on this machine and remains a release gate. V6 filed as issue #31. Per-item results are recorded below; the original procedures are kept intact.

Why these gaps exist

Three different reasons, worth keeping apart because they call for different responses:

  • The harness cannot reach it. The suite drives Rust functions, not the Tauri application. Killing the app mid-operation is outside what cargo test can express.
  • The environment is single. One machine, one filesystem, one OS. Claims about a second machine, a separate mount, or Windows are untested by construction.
  • Known and deliberately out of scope. Real, pre-existing, and wider than this ticket.

The automated crash test that does exist (killing_the_app_mid_notebook_move_still_recovers) SIGKILLs a real child process performing a real notebook move across 40 timings, then runs the real startup sequence. It is the strongest repeatable form of AC 5, and it found two defects the ordinary suite could not. It is still not the application.

V1 — Kill the running app mid-move Acceptance criterion

“Interrupting a note move mid-flight and restarting still recovers, with recovery state read from its new location — verified by actually killing the app mid-operation, not by a unit test.”

Procedure

  1. Build and run the real app: pnpm tauri dev.
  2. Create a notebook under Projects/ with roughly 300–500 notes, so the move takes long enough to interrupt. Reuse the generator shape from the crash test rather than clicking: write the files directly into the vault, then open the vault in the app.
  3. Note the machine-local directory for that vault: ~/.local/share/helixnotes/vaults/$(cat <vault>/.helixnotes/vault_id)/.
  4. Start a move of that notebook to Archives/ from the UI.
  5. While it runs, from another terminal: pkill -9 -f 'second-brain|helixnotes'. Use SIGKILL — SIGTERM would let cleanup run and prove nothing.
  6. Inspect before restarting: confirm relocation/<uuid>/directory-move.json exists in the machine-local directory and that .helixnotes/ contains no relocation-recovery/. This is the part of the criterion about the new location.
  7. Restart the app and open the same vault.

Pass criteria

  • Every note is present exactly once, wholly on one side of the move, with intact content.
  • The machine-local relocation/ directory is empty afterwards.
  • No repair banner, or a repair banner that names real paths and clears on retry.
  • .helixnotes/staging/ is gone or empty.

Repeat at least five times, varying when the kill lands — early (during the directory rename) and late (during per-note rewrites) exercise different code. If the app is too fast to interrupt reliably, raise the note count rather than adding a sleep to production code.

On failure

Capture the vault and the machine-local directory before reopening — reopening runs the sweep and destroys the evidence. cp -a both, then attach to the ticket.

V2 — Second machine, first open Acceptance criterion

“The search index rebuilds correctly from its new location, including for a vault opened for the first time on a second machine.”

Currently supported by reasoning plus the deleted-directory rebuild test: machine B is the same code path as a missing machine-local directory. That is an argument, not a run.

Procedure

  1. On machine A, use a vault until search works. Confirm .helixnotes/vault_id exists.
  2. Copy the whole vault folder to machine B — rsync -a, no exclusions. Copying everything is the point of the ticket; an exclusion list would test the thing #27 exists to remove.
  3. Do not copy ~/.local/share/helixnotes/.
  4. Open the vault on B and search for a term you know is in an old note.

Pass criteria

  • The vault opens without error and search returns correct results on B.
  • B creates vaults/<same id as A>/search/ under its own data directory.
  • B's vault_id is unchanged — identical to A's.
  • Nothing new appears inside .helixnotes/ on B beyond ordinary vault content.

A second machine is not strictly required: a second Linux user account, or the same binary with XDG_DATA_HOME pointed elsewhere, reproduces it faithfully and is far cheaper. Use that as the routine form and a real second machine once before release.

V3 — Vault on a separate filesystem Design claim

The entire justification for keeping .helixnotes/staging/ inside the vault is that publishing a note is fs::rename(staged, note) and would fail with EXDEV across mounts. That claim is load-bearing for the ADR amendment and has never been run against an actual separate filesystem. The copy-fallback in machine_local::move_path is likewise never exercised.

Procedure

  1. Create a separate filesystem and put a vault on it: truncate -s 512M /tmp/vault.img && mkfs.ext4 /tmp/vault.img, then mount it.
  2. Confirm it really is separate: stat -c %d on the vault and on ~/.local/share must differ.
  3. Open the vault, rename a note (exercises rewrite_file), move a notebook between categories, and run V1's kill test once on this vault.
  4. Separately, seed a legacy vault on this mount (a .helixnotes/relocation-recovery/ and a sync_state.json) and open it, to force move_path down its cross-device copy branch.

Pass criteria

  • No EXDEV / “Invalid cross-device link” anywhere in the log.
  • Migration completes; the legacy files are gone from the vault and present in the machine-local directory.

V4 — Machine-local state deleted while running Acceptance criterion, partly covered

“A vault whose machine-local directories are deleted outside the app recovers by rebuilding them, not by failing to open.”

A unit test covers deletion between opens. It does not cover deletion while the app holds the vault, which is when a live Tantivy index has open file handles.

Procedure

  1. With the app open on a vault, rm -rf ~/.local/share/helixnotes/vaults/<id>.
  2. Search, edit a note, rename a note, and move a notebook — without restarting.
  3. Restart and repeat the same operations.

Pass criteria

  • No crash. Degraded search before restart is acceptable; data loss is not.
  • After restart the vault opens, the directory is rebuilt, and search works again.

V5 — Windows Environment

The repo targets Windows and Linux. Everything above ran on Linux only. Windows differs in ways this change touches directly: sync_directory is a no-op there, path separators reach the origin marker, and dirs::data_local_dir() resolves elsewhere.

Minimum

  • Run the Rust suite on Windows — the crash test is #[cfg(unix)] and will skip, so V1 must be done by hand there.
  • V1 once, using Task Manager → End Task rather than pkill.
  • Confirm the origin marker round-trips: a note in a nested notebook, renamed, recovers to the right path. The marker stores a relative path written with the platform separator; a backslash path must not be read back as a single flat filename.

V6 — The replacement.md collision File, do not fix here

Pre-existing and unrelated to this ticket's goal, but now easier to reach. rewrite_file stages its rewritten copy as replacement.md inside the transaction directory, and claims the original into the same directory under its own filename. A note genuinely named replacement.md collides with the staged copy.

rescue_legacy_staged_notes also treats a file named replacement.md as derived and discards it, so in a legacy vault the collision could cost that note.

Action: open an issue referencing vault/relocation.rs rewrite_file. The fix is to stage under a name that cannot collide — a reserved subdirectory, or a name derived from the transaction id. Out of scope for #27; do not widen this branch to take it.

One false alarm worth recording

V1's first run showed all 400 notes moved to .helixnotes/unfiled/ rather than staying in the notebook, which looked like data loss. It was not: the fixture notes carried no category frontmatter field, and para.rs documents that “the note's own category field is the only source of truth”, so reconciliation correctly swept them to the holding area. A control vault with a proper category field kept 30/30 notes in place. para.rs is untouched by this branch.

Suggested order

V1 first — it is the criterion most likely to fail and the most expensive to discover late. V3 next, because if the EXDEV claim is wrong the ADR amendment is wrong and the design changes. V2 and V4 are cheap and can run in any order. V5 is a release gate rather than a merge gate if Windows is not to hand. V6 is paperwork.
