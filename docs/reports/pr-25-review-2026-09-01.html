Steps 5–7 · 2 September 2026

Unavailable-vault notification, opt-in autostart, Linux hotkey settings — all three verified live on GNOME/Wayland after the defects below.

Every defect in this round was invisible to the test suite and to review. Each was found by running the feature and watching it fail, and each is recorded here because the class of mistake is more useful than the instance.

DefectHow it presentedResolution
tauri-plugin-notification cannot be called from this app at all Every hotkey press panicked with "Cannot start a runtime from within a runtime"; the user saw nothing. The plugin schedules notify-rust's blocking call onto the tokio runtime itself, so moving the call site to a blocking-pool thread and then to a plain OS thread changed nothing — three attempts, identical panic, resolved only by reading the backtrace. Plugin removed entirely. Notifications now go through ashpd's notification portal, which is async to begin with and shares the bus connection the shortcut already uses. Net effect: one fewer dependency than before the step began.
Registry.Register is once per bus connection The settings button ran a second handshake and the portal answered "Connection already associated with an application ID", so the UI reported the shortcut as refused while it was working perfectly. Treated as success, since that is what it means. Matched on message text because the portal reports it as a generic Failed, and covered by a test carrying the portal's exact wording.
ConfigureShortcuts does not exist on this desktop "This interface requires version 2, but 1 is available". The method arrived in GlobalShortcuts version 2; GNOME 50 publishes version 1 — which ADR-0001's own verification table had recorded since 30 August, while the prose beside it listed the method as available and a settings button was built on it. Version is read from the proxy at registration and carried in the hotkey status. The UI offers the button only where it can work, and otherwise says to use the desktop's own Keyboard settings. ADR-0001 corrected.

Also found, and worth knowing before designing around it: the app recreates a missing vault directory on open (ensure_vault_structure scaffolds idempotently). A vault that vanishes between launches is therefore silently re-made rather than reported, so the unavailable-vault path only applies to a vault that disappears while the app is already running. That is the case that was tested.

Verified liveEvidence
Unavailable vault notifies instead of opening a doomed overlay Vault moved away mid-session; hotkey pressed; desktop notification appeared naming the path, no overlay, and zero panics in the log.
Autostart writes and removes a real XDG entry Enabled: entry written to $XDG_CONFIG_HOME/autostart/, app-id basename, quoted absolute Exec; parses under GLib and passes desktop-file-validate. Disabled: removed. Verified both through the startup resync and through the settings toggle.
Settings shows a read-only trigger and no dead button "Bound to Press <Control><Alt>n", with guidance to the desktop's Keyboard settings in place of the unavailable ConfigureShortcuts button.

Suite after this round: 228 Rust tests passing, 1 ignored (the live-portal test); 41 frontend tests; pnpm verify green end to end.

Before #4 can close

All seven steps are built. What remains is verification, not construction — and the pattern of this ticket is that verification is where the defects were.

Nine defects have been found in this feature so far. Every one of them was found by running it, not by testing or reviewing it — the suite was green before each. That is the argument for finishing the list below rather than closing on a green build.

OutstandingWhat it needsCost
Focus returns to the previously active application after capture Press the hotkey from another window, file a note, confirm focus returns there. A running app. Minutes.
Capture works whether or not the main window is open Close/hide the main window, then press the hotkey. A running app. Minutes.
A captured note is immediately findable Capture a note, then search for it in the app. Rests on index_note_now being synchronous and error-checked; that reasoning has not been confirmed against the search UI. A running app. Minutes.
The hotkey reports a stated reason wherever the portal cannot serve it Partly seen already: an app id the portal rejected surfaced its reason live. The remaining check is removing the dev desktop entry and relaunching, which should report AppIdRejected naming scripts/dev-desktop-entry.sh. A running app. Cheap and reversible.
A dismissed permission dialog is reported as such, with the reset command flatpak permission-reset io.github.zulucodedesign.SecondBrain, relaunch, dismiss the dialog deliberately, confirm the message names the reset command, then reset once more and re-grant. Spends a sticky decision. The portal remembers a dismissal per app id, and the permission store is per user — a sandboxed XDG_CONFIG_HOME does not isolate it. Deliberate, and needs a person at the keyboard.
Installed .deb / RPM behaviour Install a built package and confirm the portal resolves the app-id-named entry that CI already byte-compares. The .deb cannot be installed on this Fedora machine; the RPM is the realistic one. A package install, not a dev run.
Execution from a built AppImage Build with NO_STRIP=true (linuxdeploy's bundled strip cannot read this toolchain's .relr.dyn sections) and run it, so the self-written desktop entry is exercised for real rather than simulated. A packaged build. Note it writes into the real ~/.local/share/applications/ unless XDG_DATA_HOME is pointed elsewhere.
Out of scope for closing #4, by the ticket's own text: Linux/X11 is marked untested and explicitly "not promised", and Windows moved to #21. Spec §5's fourth step, the AI similarity check at capture time, is deliberately not in #4 either: it is issue #9, already blocked by #4 and by #7 (note embeddings). So the capture flow shipping without it is sequencing, not an omission — an earlier revision of this report called it an untracked gap, which was wrong.

On tooling: the dev server is an artefact of running a debug build, which loads its frontend from localhost:5173. A release build embeds the frontend and needs no server — and is closer to what users get, so the remaining checks are better run against one. The throwaway vault and config are still worth keeping so tests never touch a real vault, but not under /tmp, which is reaped and took the sandbox with it mid-session on 2 September.
