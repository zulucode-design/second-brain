Pull request 25: the quick-capture hotkey

This is a review of pull request 25. The pull request does step 1 and step 2 of ticket 4. It does not do step 3 to step 7. Two reviews were made at the same time. One review examined the repo standards. One review examined the ticket. The two reviews are kept apart, because code can obey the standards and do the wrong task. Date: 1 September 2026.

What this pull request does

Context, in short

Quick capture lets the user write a note without first finding the app. The user pushes a hotkey. A small capture overlay opens above the other windows. The user types the text, selects a PARA category, and the app files the note in the vault.

On Linux, the app cannot take the hotkey by itself. The desktop keeps control of the hotkey. The app speaks to the desktop through the portal, an interface named org.freedesktop.portal.GlobalShortcuts. The app sends a preferred trigger as a proposal only. The desktop makes the decision. ADR-0001 gives the reason for this design.

The portal identifies the app by its app id. The portal accepts an app id only when it can find an installed desktop entry with the same name. A desktop entry is a .desktop file.

This pull request contains three parts. First, it claims the app id io.github.zulucode_design.SecondBrain. Second, it decides the registration state and the message for each failure. Third, it speaks to the portal. There is no capture overlay yet. That is step 3.

Test on the true portal. The registration was tested on GNOME and Wayland on 1 September 2026. The first run showed the permission dialog and made the binding. It took 18.8 seconds. Almost all of that time was the dialog. The second run found the binding again. It did not show a dialog. It took 0.03 seconds. This proves that the app asks for permission one time only.

Review 2 — the ticket

4 findings. One is important.

Finding 1. The installed app will not register the hotkey.

Ticket 4 says: “with an installed .desktop whose basename matches”. The pull request changes the app id in tauri.conf.json. But it does not set a name for the desktop entry in the bundle.linux section. Thus the build tool makes the name from the product name. The result is HelixNotes.desktop. The portal looks for io.github.zulucode_design.SecondBrain.desktop. The two names are different.

The development build operates correctly, because the script writes the correct name. The installed build will fail. It will fail with the message “App info not found”. This is the same silent failure that ticket 4 must prevent.

Finding 2. The status type does not obey the instruction. Ticket 4 says: “Status surface reuses the Availability + reason shape from ai_health.rs”. The file ai_health.rs has the values Unknown, Available, and Unavailable. The new code makes a second enum. It uses Registered in the place of Available. Thus the user interface cannot use one type for both. The rest of the shape is correct.

Finding 3. Some code belongs to a later step. The constants ACTIVATED_EVENT and STATUS_EVENT belong to step 3 and step 7. The function configure() is the settings button of step 7.

Finding 4. Two comments disagree. The comment at the top of portal.rs says that a drop of the Registration gives up the hotkey. The comment on the type says that a drop closes nothing. There is no Drop code and no call to session.close().

These decisions from the ticket are correct in the code:

  • The code uses the portal only. There is no X11 grab.
  • The code asks the portal for the list of shortcuts first. It makes a binding only when a binding does not exist.
  • The code sends the trigger as a proposal. It shows the description from the portal and does not read it as a key name.
  • The code reports a refused permission as its own state. The message contains the command flatpak permission-reset.
