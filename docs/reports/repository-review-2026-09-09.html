Executive summary

This is a substantial Tauri/Svelte desktop notes application, not a throwaway prototype. It has strong foundations around plain-Markdown ownership, PARA filing, crash-recoverable relocation, machine-local search, filesystem watching, global quick capture, and secure public-web clipping. The exact reviewed commit type-checks, passes all frontend tests, builds successfully, and passed the complete Linux verification and packaging workflow.

The highest risks are concentrated in older persistence and synchronization paths that do not use the same transaction and containment principles as the newer relocation subsystem. The most urgent sequence is:

  1. Constrain WebDAV paths and reject symlink escapes.
  2. Make restore staged and transactional.
  3. Serialize sync with edits and vault transitions.
  4. Make note/config/manifest writes crash-safe.
  5. Repair editor save ordering and close behavior.
  6. Add fault-injection and cross-platform integration coverage.
Important: no application code or configuration was changed during the review. The only repository change associated with this deliverable is this approved HTML report.

What works well

Local-first source of truth

Markdown/YAML remains authoritative while search is derived and rebuildable. This is the right ownership model for a durable notes application.

PARA enforcement

The four categories are enforced below the UI. Metadata drives reconciliation, unresolved notes enter a holding area, and category roots are protected.

Transactional relocation

Moves, renames, delete, and restore use staging, identity/content checks, recovery copies, manifests, rollback, and filesystem synchronization.

Vault identity

Machine-local identity claiming uses locking and cautious recovery instead of allowing competing or silently replaced identities.

Search and watcher design

Tantivy indexing is incremental and machine-local. External events are coalesced and interpreted from final filesystem state, improving cross-platform behavior.

Secure public fetching

Clipping and image fetching reject private destinations and URL credentials, pin DNS results, revalidate redirects, and cap response sizes.

Quick capture safeguards

The capture window has minimal capabilities, preserves text on failure, requires explicit filing, and protects against accidental dismissal.

Linux delivery checks

CI performs full project verification, builds deb and rpm packages, and validates the desktop entry required by the Linux global-shortcut design.

Critical finding

SEC-01 — WebDAV remote paths can escape the vault

Critical · high confidence

Server-controlled WebDAV href paths are percent-decoded, stripped using lexical string-prefix logic, and returned without rejecting parent components, roots, platform prefixes, backslashes, or decoded separators. The resulting string is later passed to vault.join(relpath) and written.

let target = vault.join(relpath);
fs::write(&target, bytes)

A malicious or compromised configured endpoint could provide a path such as an encoded ../outside.md and potentially overwrite files outside the vault with the application user's permissions. An existing symlink in the destination path can produce a similar escape.

Required correction: construct validated portable path components; reject dot/parent/root/prefix and decoded separator forms; require a component-boundary match with the configured base; use no-follow destination opens; and recheck containment beneath the canonical vault before committing a write.

Evidence: src-tauri/src/sync.rs:129-134, src-tauri/src/sync.rs:403-436, and download/conflict writes in src-tauri/src/sync.rs:522-703. The current sync test covers only the synced-path allowlist, not hostile href mapping.

High-severity findings

DATA-01 — Backup restore deletes live data before extraction is proven

High · high confidence

Restore opens the ZIP, deletes all visible vault content and attachments, and then extracts directly into the live tree. A corrupt later member, CRC/decompression failure, permission error, disk-full condition, or process termination can leave the vault empty or partially restored.

Recommendation: validate quotas and entry types, extract into a sibling staging tree, fsync it, and atomically swap it with the live tree while retaining a rollback copy. Serialize restore against edits and vault transitions.

Evidence: src-tauri/src/backup.rs:182-259; restore command threading in src-tauri/src/commands.rs:2884-2917.

DATA-02 — Pre-switch save can clear dirty state without a successful save

High · high confidence

Normal autosaves use a promise queue, but flushSave() bypasses it. It calls asynchronous saveNote() without awaiting, queueing, or catching a rejected promise, then unconditionally clears editorDirty. Its synchronous try/catch cannot catch asynchronous rejection.

The same path refuses to save an empty body over a previously substantial note, so a user cannot intentionally clear a note through normal save paths.

Recommendation: make navigation await an immutable queued save request; clear dirty state only after success; preserve and expose failed state; and replace the content-length heuristic with explicit serialization-validity handling that permits intentional empty notes.

Evidence: queue/autosave at src/lib/components/Editor.svelte:3014-3068; unsafe flush at src/lib/components/Editor.svelte:3303-3320.

DATA-03 — Sync decisions race active note edits

High · high confidence

Sync prevents overlapping sync jobs but does not acquire the normal note mutation lock. It scans hashes first, then later applies decisions from that stale snapshot. A note edited after scanning can still be deleted by the remote-deleted/local-unchanged branch.

Recommendation: coordinate sync through a vault-scoped transaction, or re-read and identity/hash-check every file immediately before destructive overwrite or delete. Failure to remove a file must not be counted as a successful deletion.

Evidence: src-tauri/src/commands.rs:3226-3261; scan/apply and deletion branches in src-tauri/src/sync.rs:522-748.

DATA-04 — Vault switching during sync can rebuild the wrong search runtime

High · high confidence

Sync captures the old vault path. At completion it retrieves whichever search index is currently active and rebuilds it using that old path. If the user changes vaults during sync, the current search instance can be populated from the previous vault.

Recommendation: bind background work to a vault ID/generation and the specific Arc<SearchIndex> captured at start. Reject side effects and events from stale generations.

Evidence: active search replacement in src-tauri/src/commands.rs:453-458; post-sync rebuild in src-tauri/src/sync.rs:750-753.

DATA-05 — Notes and application configuration are not atomically replaced

High · high confidence

Ordinary note saves use direct fs::write. Application config opens the live file with truncate(true). A crash or disk-full event can leave either file truncated. Existing unreadable or malformed application config silently becomes AppConfig::default(), making vault registrations, settings, and credentials appear lost.

The sync manifest has the same direct-write/default-on-corruption pattern; its isolated impact is lower, but corruption changes three-way reconciliation history.

Recommendation: use one same-directory temp + write + sync_all + atomic replace + parent-fsync primitive. Preserve a verified prior generation and surface corruption rather than silently defaulting.

Evidence: notes at src-tauri/src/vault/operations.rs:618-637; config at src-tauri/src/commands.rs:3398-3481; manifest at src-tauri/src/sync.rs:59-84.

SEC-02 — File symlinks can cross the vault boundary

High · high confidence

Bulk scanners do not recursively follow directory symlinks, but they can treat file symlinks as regular files because they use target-following is_file, File::open, and fs::read. This can upload or back up an outside file. A sync download onto an existing file symlink can overwrite the outside target.

Recommendation: reject symlink entries via directory-entry file types and symlink_metadata; use no-follow opens for destination files; and apply the normal note-path containment policy to every bulk workflow.

Evidence: sync scanning/writes in src-tauri/src/sync.rs:129-168; backup scanning in src-tauri/src/backup.rs:66-106.

Product and specification alignment

The running product is a capable local-first Markdown application, but several defining features described in the README and authoritative SPEC are not implemented. The documentation should distinguish target architecture from shipped behavior.

Implemented now

  • Plain Markdown/YAML storage
  • PARA filing, holding area, and reconciliation
  • TipTap and source-mode editing
  • Windows/Linux global quick capture
  • Tantivy keyword/fuzzy search
  • Explicit wiki-link graph
  • Tasks, attachments, trash, history, and backups
  • Security-hardened URL clipping
  • In-process WebDAV synchronization
  • Local or cloud AI writing assistance

Documented but not found

  • SQLite embedding storage and semantic search/Q&A
  • Capture-time similarity or duplicate detection
  • Semantic graph edges and link promotion
  • Voice recording and whisper.cpp transcription
  • Bundled synchronization sidecar via externalBin
  • Explicit device pairing and Tailscale workflow
  • Notion publishing
  • Conflict-pair review and choose-one UI

Primary contradictions

  • Sync: the SPEC says the project does not author the sync engine and uses a bundled sidecar; the code authors an in-process WebDAV reconciler.
  • Sync boundary: the SPEC says trash/history sync; the current path explicitly excludes them.
  • AI privacy: README language presents local/no-cloud AI, while the settings support Anthropic, OpenAI, Ollama, and arbitrary OpenAI-compatible providers.
  • Brand/release identity: user-facing product docs say Second Brain while package, updater, config, and UI areas retain HelixNotes identity.
  • Platform scope: README advertises Windows/Linux and the SPEC excludes mobile, while inherited mobile-specific paths remain in the codebase.
Recommendation: add a maintained feature-status matrix with Shipped, In progress, and Planned. Treat the sync architecture decision as a product decision before treating implementation and documentation drift as a simple cleanup.

Testing and delivery assessment

Existing strengths

Rust tests substantially cover PARA rules, relocation recovery, vault identity, watcher behavior, search reconciliation, frontmatter, safe-fetch URL policy, clipping, and repair persistence. Frontend tests cover policy and utility behavior for creation, paths, PARA UI, virtualization, startup, sync settings, Markdown round-tripping, and clipping.

Highest-value missing tests

  1. Encoded WebDAV traversal, base-prefix confusion, Windows drive/UNC forms, and symlink destinations.
  2. Sync/edit race, vault switch during sync, manifest corruption, server without reliable ETags, and two-machine convergence.
  3. Restore archive corruption, disk-full, expansion quotas, process interruption, and rollback.
  4. Editor save ordering, intentional empty-note save, close during debounce, and failed persistence.
  5. Simultaneous AI requests from multiple windows and exact request correlation.
  6. Rendered Svelte interaction and native Tauri launch/edit/reopen/capture/tray smoke tests.

Delivery gaps

  • The sole CI runner is Ubuntu; Windows- and macOS-specific native code is not compiled or packaged in CI.
  • There is no complete signed release, notarization, updater-metadata, clean-install, or rollback workflow.
  • Supply-chain automation such as advisory checks, license policy, SBOM, and provenance is absent.
  • The updater configuration retains inherited infrastructure and should be validated for ownership and key custody before release.

Prioritized remediation roadmap

  1. Release-blocking security and data safety

    1. Fix WebDAV path construction and add no-follow destination writes.
    2. Make restore staged, bounded, atomic, and recoverable.
    3. Serialize sync with note mutations and vault transitions.
    4. Revalidate identity/hash immediately before sync delete or overwrite.
    5. Bind every background job and completion event to a vault generation.
    6. Reject symlinks consistently in sync, backup, import, and restore.

  2. Persistence correctness and editor lifecycle

    1. Introduce a shared crash-safe atomic-write primitive.
    2. Use it for notes, config, sync manifest, notebook icons, and import rewrites.
    3. Preserve corrupt files and expose repair state instead of silently defaulting.
    4. Replace flushSave() with an awaited save coordinator.
    5. Permit intentional empty notes through explicit validation.
    6. Add a close/save handshake and persistent save-error UI.

  3. Correctness visibility, tests, and platform confidence

    1. Correlate and cancel AI stream requests.
    2. Report partial search/import failures through the repair and operation UI.
    3. Add hostile-input and fault-injection suites for sync, restore, and writes.
    4. Add Windows and macOS CI plus a minimal integrated desktop smoke suite.
    5. Reconcile README, SPEC, ADRs, and shipped behavior.
    6. Decide whether WebDAV or a bundled sidecar is the supported sync architecture.

  4. Scale, maintainability, accessibility, and release polish

    1. Move graph layout to a worker and replace all-pairs repulsion.
    2. Extract persistence, AI, attachments, graph, modal, theme, and operation-status services from monolithic components.
    3. Restore user zoom and text selection; complete modal and graph accessibility.
    4. Remove the broad /tests/ ignore rule.
    5. Complete product rebranding, updater ownership, signing, and release documentation.

Known limitations and unverified areas

This review was primarily static and did not claim to prove runtime behavior that requires real desktop environments, remote services, accessibility tooling, or fault injection. Before release, manually or automatically verify:

  • Power-loss and disk-full behavior for note, config, restore, import, and sync writes.
  • Hostile WebDAV listings, encoded paths, oversized responses, unstable/no ETags, TLS/auth behavior, and interrupted reconciliation.
  • Window close timing and process shutdown while saves or background jobs are active.
  • Windows global shortcut conflicts, autostart, notifications, installer behavior, and native close lifecycle.
  • Linux portal behavior across representative Wayland/X11 desktop environments.
  • Graph performance at 1k and 10k notes.
  • Keyboard-only, screen-reader, reduced-motion, high-contrast, and zoom behavior.
  • Raw HTML/URL payload handling through clipping and imported Markdown in the final TipTap DOM.

Conclusion

The repository has a strong core and several examples of excellent engineering, particularly transactional relocation, PARA enforcement, vault identity, machine-local search, watcher coalescing, capture isolation, and safe public-web fetching.

The central inconsistency is that newer safety-focused subsystems are robust while ordinary saves, restore, import, and WebDAV do not yet use the same containment and transaction model. Applying the relocation layer's durability discipline across those workflows would eliminate much of the current risk.

Recommended order: WebDAV containment → transactional restore → sync/edit serialization → atomic persistence → editor save lifecycle → targeted tests → additional product features.
