Ticket #18 — AI provider identity and probeable backends

Updated 2026-09-08. This report records the implementation and automated evidence for replacing scattered provider strings with explicit, capability-based provider contracts.

What changed

  • Rust configuration now stores an AiProvider enum while serializing the same existing IDs. Unknown legacy IDs survive a load/save cycle instead of invalidating the config.
  • ConfiguredAiProvider owns key selection, configurable-address behavior, API-key requirements, probeability, and health-target construction.
  • The health probe supports both Ollama's /api/tags response and the OpenAI-compatible /v1/models response, including optional bearer authentication.
  • Fast refusal is provider-independent and applies only to an unavailable result for the exact current target generation. Switching provider, endpoint, model, protocol, or credentials invalidates stale health.
  • TypeScript uses an AiProvider union and exhaustive capability table. Both local provider choices display live status and the manual “Check now” action.

Review remediation

The final independent re-review found 0 Standards violations and 0 Spec findings. The Standards axis raised one judgement call about repeated exhaustive provider/protocol matches. It was retained intentionally: those matches are centralized in the provider and health modules and make a newly added case fail compilation until its capabilities and wire behavior are handled, as ticket #18 requires.

  • The provider profile now resolves one secret-safe request-settings object, eliminating duplicate URL normalization, repeated provider dispatch, and repeated settings tuples.
  • OpenAI-compatible model discovery accepts Ollama's bare-name to :latest equivalence, preventing false unavailability for the same Ollama model.
  • The exhaustive frontend metadata drives provider buttons, keys, model controls, privacy text, defaults, and server behavior. The shared status snippet preserves the existing Ollama Server URL → Status → API Key order.

Manual verification

Passed on 2026-09-08 using the Linux/WSLg development build and a disposable local server that exposed both Ollama and OpenAI-compatible discovery contracts.

  1. Selected OpenAI Compatible with http://127.0.0.1:18018/v1 and gemma3. The app normalized the displayed target to http://127.0.0.1:18018, matched the advertised gemma3:latest, reported reachable, and passed “Test Connection.”
  2. Ran an editor AI action, received the fixture's streamed response, previewed it, and replaced the selected text successfully.
  3. Stopped the server and used “Check now.” Settings displayed an actionable OpenAI-compatible-specific reason with no Ollama wording; the editor refused the next AI action immediately with the same reason and left the note unchanged.
  4. Restarted the server. Background probing restored reachable status and a second AI action succeeded without restarting HelixNotes.
  5. Switched to Ollama and back to OpenAI Compatible. Both protocols independently reached the dual-protocol fixture without restarting the app.
