1. Operating model

  1. This plan is the stable map. GitHub issues are the executable tickets and must link back to this report and the audit finding IDs.
  2. Each work package lands in its own focused pull request unless its ticket is documentation-only. Do not combine independent P1 fixes.
  3. For behavioral fixes, reproduce the defect with a failing test first wherever the boundary is testable. Preserve the regression test after remediation.
  4. Every mutation-related PR states its transaction boundary, failure behavior, watcher behavior, keyword-index effect, semantic-index effect, and UI refresh effect.
  5. Every completed ticket updates the audit status instead of deleting historical findings. The report remains the evidence record.
  6. Use pnpm test:rust, never bare cargo test. The merge gate is pnpm verify plus relevant package/platform checks.

4. Recommended execution order

  1. Wave 0 — decisions and containment: disable risky external-alpha surfaces; resolve G1–G4. Start H’s Windows/CI scaffolding.
  2. Wave 1 — independent P1s complete: A/B/C complete / verified PR #90 fixed save lifecycle, PR #93 delivered transactional restore and the shared coordinator, and PR #94 removes WebDAV.
  3. Wave 2 — coordinated mutation adoption: D adopts C’s coordinator for the selected sync architecture, then E adopts it for import. Keep each PR independently reviewable.
  4. Wave 3 — durability and visible correctness: F and G.
  5. Wave 4 — verification closure: complete H against the implemented failure scenarios, including package installation/smoke evidence.
  6. Wave 5 — product alignment: I and G3/G4 migrations.
  7. Wave 6 — scoped feature completion: J according to G2, followed by a fresh audit delta and alpha sign-off.

5. Per-ticket workflow

  1. Claim: assign one ready ticket and state the intended invariant.
  2. Reproduce: add the smallest failing test or a deterministic verification fixture. For platform-only behavior, record a manual protocol before implementation.
  3. Implement: preserve Markdown as canonical; indexes remain disposable projections. Avoid introducing a second mutation path.
  4. Verify locally: targeted test first, then pnpm verify. Run deb/rpm verification for packaging/platform changes.
  5. Review: require both behavioral/spec review and code-quality review. Data mutation PRs include failure and interruption analysis.
  6. Publish: one focused PR linking the ticket and this plan. Do not merge with unresolved P1 review findings.
  7. Close the loop: update the source audit finding to fixed/accepted/deferred with commit and verification evidence; close the ticket only after CI.

6. Definition of external-alpha ready

  • A/B/C complete / verified D and H remain; no open P0/P1 data-integrity or security issue at release.
  • G1–G4 are recorded and their required outcomes are implemented in SPEC, README, settings, packaging, migrations, and executable tickets.
  • H’s versioned verification-matrix record is complete and green: commands, supported Linux/Windows platforms, fixtures, manual protocols, expected outcomes, evidence links, performance thresholds, and residual gaps are explicit.
  • pnpm verify is green at documented Node/pnpm/Rust versions on Linux and Windows.
  • Package build and install/launch smoke pass for every supported Linux format and Windows package.
  • Automated end-to-end tests prove edit/navigation/close durability, restore rollback, hostile sync-path rejection or WebDAV unreachability, and interrupted bulk reconciliation.
  • A clean disposable-vault manual protocol covers capture, editing, search, tasks, trash/history, backup/restore, clipping, AI-offline degradation, the selected two-machine sync/conflict flow, and Notion publication.
  • Audit checklist has no unresolved blocker; every deferred v1 item and accepted architecture debt names its target milestone.
