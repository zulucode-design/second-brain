What the interactive pass fixed

1

The capture window was never declared on Windows

523883a — tauri.windows.conf.json

Feature dead
Symptom

Pressing the hotkey did nothing. No overlay, nothing in Alt+Tab, no notification, no error — on every build.

Cause

The capture window existed only in tauri.linux.conf.json. Tauri's per-platform config replaces the app.windows array rather than merging into it, so on Windows the app's window set was ["main"].

Chain
  • ensure_window searched the config for label "capture", found nothing, and returned an error.
  • spawn() treats that as fatal and returns early — so the hotkey was never registered at startup at all.
  • Setting it manually in Settings calls apply_trigger directly, which never touches the window, so registration genuinely succeeded and the UI looked healthy.
  • Every later activation reached show_capture_window, found no window, and logged a warning into a release build with no log plugin.
Also affects macOS

tauri.macos.conf.json declares only main as well. Whenever quick capture reaches macOS it will fail identically. Out of scope for #21; the same one missing block.

2

The window came up visible, and outlived the app

7d8a9c2 — hotkey/window.rs

Unkillable window
Symptom

After fix 1, the overlay appeared at launch, unprompted, parked over whatever else was on screen — and survived closing the main window, leaving a process only Task Manager could end.

Cause

Tauri creates this window from config before our code runs, and on Windows it came up visible regardless of the config's own "visible": false.

Evidence

A debug build printed no "Capture window ready" line, which only the branch that builds the window logs — proving ensure_window's is_some() early return was what ran, and something else had already created it. ensure_window now hides the window itself once it knows it exists, whichever path found it, rather than trusting the flag. That is what its own name already promised.

3

The overlay had no permission to dismiss itself

d043b56 — capabilities/capture.json

Stuck open
Symptom

A note saved correctly, then the overlay stayed on screen showing Command plugin:window|hide not allowed by ACL, with no way to dismiss it.

Cause

capture.json scoped itself to "platforms": ["linux"]. default.json covers only main and note-*, so the capture window had no ACL grant on Windows at all.

Pattern

Third instance of the same family as fix 1: a Linux-only assumption written before a Windows capture window existed, never widened when it gained one.

4

A rejected hotkey change killed the working one

b4f8b7a — hotkey/windows.rs

Silent data-loss-shaped
Symptom

Rejecting a conflicting trigger left the previously-working hotkey permanently dead — precisely what item 2's own acceptance criterion says must not happen.

Cause

apply_trigger called unregister_all() unconditionally before attempting the new trigger, with no path that restores the old one on failure.

Fix

Register the new trigger first; only on success drop the specific old one — unregister(), not unregister_all(), which would tear down the registration just added, since the plugin tracks by shortcut value rather than by "the app's current hotkey". A failed attempt now touches nothing. Startup's own call is unaffected: its trigger equals the configured value, so there is nothing to drop.

Why every earlier test missed this

Every prior conflict attempt was made by physically pressing the combination, and none of them ever reached apply_trigger at all (see the keystroke limitation below). "The old shortcut still works" had been observed repeatedly and meant nothing — the failing code had never run. It surfaced only once the command was invoked directly, bypassing the keyboard.

5

The Settings-driven path logged nothing at all

af29cdd — hotkey/windows.rs

Undiagnosable
Cause

apply_trigger had no logging: a parse failure, a failed unregister_all(), and a failed registration all returned or proceeded silently. This contradicts the principle already stated in startup.rs and applied to the startup path — "An unregistered hotkey is invisible by nature — nothing happens when the key is pressed — so the reason has to be somewhere a person can read it without attaching a debugger." The manual-change path simply never got the same treatment. Fix 4 was only findable after this was added.

The keystroke limitation, and what it costs

This one is not a defect and cannot be patched; it is a property of the platform that constrains what the settings UI can ever do.

Once any process holds a combination via RegisterHotKey, Windows stops delivering that combination as an ordinary keystroke to whatever window has focus. It goes to the registering process as WM_HOTKEY and nowhere else.

The settings panel captures a shortcut by listening for a DOM keydown. So for exactly the conflicts worth reporting — a combination genuinely claimed at the OS level — the webview never receives the keystroke, invoke is never called, and the backend is never asked. The button sits in "Press a key combination…" indefinitely and no message appears, because none was ever generated.

This is what #21 bills as its differentiator: "a real conflict is reported by name — the one thing this backend can say that Linux structurally cannot." The backend can say it, and does, correctly. The capture field cannot ask the question. Surfacing it through normal use would mean capturing keys with a native low-level keyboard hook (WH_KEYBOARD_LL) instead of DOM events — a real architectural change, deliberately not attempted here.

It also invalidated four earlier conflict tests in this session, each of which looked like a UI bug and was not. Anything that reports on this path needs to state which mechanism holds the conflicting key: a RegisterHotKey claim behaves entirely differently from a low-level hook, which is why ShadowPlay's Alt+Z opened its overlay while ours never saw the key.

Found here, not fixed here

Surfaced by this pass, but none of it is #21's code. Recorded so the next person does not rediscover them from scratch.

Tray: a click cannot restore a destroyed main window

lib.rs, setup_tray. Both the tray handler and the single-instance callback re-show main only if let Some(window) = …get_webview_window("main"). With close-to-tray off, closing the window destroys it, so that is None and both paths silently do nothing — the app is running, invisible, and unreachable. Pre-existing; not in this diff.

Tray: right-click raises the window instead of opening the menu

lib.rs. The handler matches TrayIconEvent::Click { .. }, discarding the button field, so a right-click also shows and focuses the window — pre-empting the context menu. That makes Quit unreachable, which with close-to-tray on leaves no graceful way to exit at all. Pre-existing; not in this diff.

Autostart opens the full window at login

The Run value carries no quiet-start flag, so a login pops the main window even with a tray icon configured. Every neighbouring value in that same key uses one — -silent, --minimized, --startup_mode, --autostarted. Behaviour question, not a defect: item 4's criterion is "launches at login", which it does.

The capture window flashes white at launch

Fix 2 hides the window as soon as our code can, but Tauri has already shown it by then, so a brief white flash remains at startup. Cosmetic, and much better than the window staying up permanently, but not nothing. Worth a follow-up if it bothers anyone in daily use.

Release builds have no logs at all

lib.rs gates tauri_plugin_log behind cfg!(debug_assertions), so every diagnostic in this module is discarded in the shipped build — including the one explaining why a hotkey is unavailable. Three of the five defects above were only diagnosable after switching to a debug build. Pre-existing, and squarely at odds with the reasoning in startup.rs about reasons needing to be readable without a debugger.
