This record keeps the two kinds of evidence separate rather than letting what was checked remotely stand in for what was not.

Needs a person at the Windows desktop

Each maps directly to one of #21's acceptance criteria.

1 — The hotkey actually works

  1. Open Second Brain, open Settings, confirm the Windows section shows "Click to set a shortcut".
  2. Click it, press a combination (e.g. Ctrl+Alt+K), release. Confirm the field now shows that combination.
  3. Switch to any other application — a browser, Notepad.
  4. Press the configured combination. The capture overlay should appear on top of whatever was focused.
  5. Type a note, pick a category, save (or press Esc to cancel).
  6. Confirm focus returns to the application that was active before the hotkey was pressed — not to Second Brain's main window.

2 — A real conflict is reported by name

  1. In Settings, try to set the hotkey to a combination already bound elsewhere — a common one to try is whatever your keyboard driver or another running app already claims (Print Screen tools, clipboard managers, and IME switchers are common culprits).
  2. Confirm the settings panel shows a message naming that specific combination as already in use, not a generic failure.
  3. Confirm the previously-working shortcut is unaffected — a failed change should not have torn down the one that was already registered.

3 — Capture works with the main window closed

  1. Close Second Brain's main window (not Quit — if "close to tray" is off, this may quit the app entirely; confirm which, since the criterion implies the hotkey should survive at least a closed main window while the process is running).
  2. Press the hotkey. The overlay should still appear.

4 — Autostart

  1. Enable "Start at login" in Settings.
  2. Open Task Manager → Startup apps, or regedit at HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run, and confirm a Second Brain entry appears with no admin prompt having been shown.
  3. Disable it again and confirm the entry is removed.
  4. Log out and back in (or restart) with it enabled, and confirm the app actually launches at login.

5 — The vault-unavailable notification

This is the one design claim in the diff that could not be exercised at all from here: whether tauri-plugin-notification's Windows backend avoids the Tokio-runtime-nesting panic that ruled it out on Linux (ADR-0001).

  1. With a vault configured, rename or move the vault folder so the configured path no longer resolves.
  2. Press the hotkey.
  3. Confirm a Windows notification appears naming the vault path, and that the app does not crash or hang. If it panics instead, that confirms the plugin's Windows backend has the same issue as Linux's, and a hand-rolled Win32 notification will be needed — file that as its own follow-up rather than blocking this ticket further, matching how ADR-0001 documented the equivalent Linux finding.
