The Windows hotkey backend: what the keyboard found

#21's own acceptance criteria say plainly: the visual and interactive parts — an overlay appearing over another application, focus returning to it, a key-capture field responding to real keystrokes — cannot be verified over a remote shell. This record keeps the two kinds of evidence separate rather than letting what was checked remotely stand in for what was not.

The interactive passes found ten real defects, every one of them invisible to the remote checks. All are closed. Item 5's actual open question — the ADR-0001 panic risk — is answered, and its remaining half is deferred to #42 as structurally untestable from any dev build; a packaged install for that is #49. Choosing the hotkey yourself is deferred to #46, gated on the release.

Everything in the remote table below was green before a person sat down at the machine, and the feature was nonetheless completely non-functional: pressing the hotkey did nothing at all, on any build, ever. Every one of the five defects sat in a file or a code path that compiles, tests, lints and type-checks clean. None of them could have been caught by anything short of pressing the key.

What the interactive pass fixed

1

The capture window was never declared on Windows

523883a — tauri.windows.conf.json

Feature dead
Symptom

Pressing the hotkey did nothing. No overlay, nothing in Alt+Tab, no notification, no error — on every build.

Cause

The capture window existed only in tauri.linux.conf.json. Tauri's per-platform config replaces the app.windows array rather than merging into it, so on Windows the app's window set was ["main"].

Chain
  • ensure_window searched the config for label "capture", found nothing, and returned an error.
  • spawn() treats that as fatal and returns early — so the hotkey was never registered at startup at all.
  • Setting it manually in Settings calls apply_trigger directly, which never touches the window, so registration genuinely succeeded and the UI looked healthy.
  • Every later activation reached show_capture_window, found no window, and logged a warning into a release build with no log plugin.
Also affects macOS

tauri.macos.conf.json declares only main as well. Whenever quick capture reaches macOS it will fail identically. Out of scope for #21; the same one missing block.

2

The window came up visible, and outlived the app

7d8a9c2 — hotkey/window.rs

Unkillable window
Symptom

After fix 1, the overlay appeared at launch, unprompted, parked over whatever else was on screen — and survived closing the main window, leaving a process only Task Manager could end.

Cause

Tauri creates this window from config before our code runs, and on Windows it came up visible regardless of the config's own "visible": false.

Evidence

A debug build printed no "Capture window ready" line, which only the branch that builds the window logs — proving ensure_window's is_some() early return was what ran, and something else had already created it. ensure_window now hides the window itself once it knows it exists, whichever path found it, rather than trusting the flag. That is what its own name already promised.

3

The overlay had no permission to dismiss itself

d043b56 — capabilities/capture.json

Stuck open
Symptom

A note saved correctly, then the overlay stayed on screen showing Command plugin:window|hide not allowed by ACL, with no way to dismiss it.

Cause

capture.json scoped itself to "platforms": ["linux"]. default.json covers only main and note-*, so the capture window had no ACL grant on Windows at all.

Pattern

Third instance of the same family as fix 1: a Linux-only assumption written before a Windows capture window existed, never widened when it gained one.

4

A rejected hotkey change killed the working one

b4f8b7a — hotkey/windows.rs

Silent data-loss-shaped
Symptom

Rejecting a conflicting trigger left the previously-working hotkey permanently dead — precisely what item 2's own acceptance criterion says must not happen.

Cause

apply_trigger called unregister_all() unconditionally before attempting the new trigger, with no path that restores the old one on failure.

Fix

Register the new trigger first; only on success drop the specific old one — unregister(), not unregister_all(), which would tear down the registration just added, since the plugin tracks by shortcut value rather than by "the app's current hotkey". A failed attempt now touches nothing. Startup's own call is unaffected: its trigger equals the configured value, so there is nothing to drop.

Why every earlier test missed this

Every prior conflict attempt was made by physically pressing the combination, and none of them ever reached apply_trigger at all (see the keystroke limitation below). "The old shortcut still works" had been observed repeatedly and meant nothing — the failing code had never run. It surfaced only once the command was invoked directly, bypassing the keyboard.

5

The Settings-driven path logged nothing at all

af29cdd — hotkey/windows.rs

Undiagnosable
Cause

apply_trigger had no logging: a parse failure, a failed unregister_all(), and a failed registration all returned or proceeded silently. This contradicts the principle already stated in startup.rs and applied to the startup path — "An unregistered hotkey is invisible by nature — nothing happens when the key is pressed — so the reason has to be somewhere a person can read it without attaching a debugger." The manual-change path simply never got the same treatment. Fix 4 was only findable after this was added.

The keystroke limitation, and what it costs — #46

This one is not a defect and cannot be patched; it is a property of the platform that constrains what the settings UI can ever do.

Once any process holds a combination via RegisterHotKey, Windows stops delivering that combination as an ordinary keystroke to whatever window has focus. It goes to the registering process as WM_HOTKEY and nowhere else.

The settings panel captures a shortcut by listening for a DOM keydown. So for exactly the conflicts worth reporting — a combination genuinely claimed at the OS level — the webview never receives the keystroke, invoke is never called, and the backend is never asked. The button sits in "Press a key combination…" indefinitely and no message appears, because none was ever generated.

This is what #21 bills as its differentiator: "a real conflict is reported by name — the one thing this backend can say that Linux structurally cannot." The backend can say it, and does, correctly. The capture field cannot ask the question. Surfacing it through normal use would mean capturing keys with a native low-level keyboard hook (WH_KEYBOARD_LL) instead of DOM events — a real architectural change, deliberately not attempted here.

It also invalidated four earlier conflict tests in this session, each of which looked like a UI bug and was not. Anything that reports on this path needs to state which mechanism holds the conflicting key: a RegisterHotKey claim behaves entirely differently from a low-level hook, which is why ShadowPlay's Alt+Z opened its overlay while ours never saw the key.

Fixed after the pass, in review

Two defects the interactive pass exposed but did not itself close — one it found directly, one it created the conditions to notice.

The overlay kept the process alive — 8051508

lib.rs's Destroyed handler closed only note-* windows when main was destroyed, which was sufficient right up until a second long-lived window existed. Tauri exits when the last window closes, so the permanently-hidden overlay held an invisible process open that no tray click and no relaunch could reach, ending only in Task Manager. Now closes every window that is not main. Latent on Linux since the overlay was added there; it took a Windows pass to hit it.

A rejected change reported a dead hotkey that was still working — 5319786

Fix 4 made a refused trigger leave the working registration alone, but apply_trigger still stored and emitted the refusal as the hotkey's state: Unavailable, trigger: None. So the old shortcut kept firing while Settings said there was no hotkey at all — the same disagreement between the UI and reality that registering-before-unregistering exists to prevent, one layer up. The rejection is still returned, so the panel can still name the conflicting combination; what is published is now whatever is actually bound. Also sources that from the published status rather than the config, which records only what the user asked for. Found in review, not at the keyboard: it needs the conflict path from item 2, which the settings field cannot reach.

The second interactive pass, 2026-09-07

#44, #45 and #46 were filed as separate issues from the first pass, then pulled back into this PR: they belong to the work done here, and merging without them would leave the Windows quick-capture path half-finished. This is what came of that.

#45 — release builds now log Verified

The cfg!(debug_assertions) gate is gone, so the logger is registered in every build. Confirmed on a real release binary: the first line written was Quick capture hotkey not registered: no vault is configured yet — hotkey::windows's own "why there is no hotkey" message, reaching a shipped build for the first time. Rotation raised from the plugin's 40 KB default to 5 MB keeping three, since 40 KB does not still hold the startup line by the time anyone looks. Paths are in the README.

#44 — the tray is reachable Verified

Right-click opens the menu and Quit works; left-click restores the window. The handler now matches the left button explicitly instead of discarding it, and turns off the plugin's show_menu_on_left_click default, which had been putting the menu on both buttons. All three restore paths — tray menu, tray click, second launch — go through one show_main_window that rebuilds the window from config when it is gone.

Registration was startup-only Fixed

Found while setting the machine up for this pass. spawn refuses to register with no vault configured, which is right, but nothing repeated the check: a first run went "choose a vault, and quick capture stays dead until restart", with settings still saying open a vault to enable quick capture to someone who just had. Opening a vault now re-runs spawn — and only when nothing is bound, since re-registering a combination this app already holds returns AlreadyRegistered and would be reported as a conflict with nobody.

#46 — the keyboard hook failed, and was removed Three rounds, no capture

A WH_KEYBOARD_LL hook (ADR-0003) is the only mechanism that can see a combination another process has claimed. It was built and tested across three rounds and never captured one. Each round found a real defect: modifiers read with GetAsyncKeyState inside a callback that runs ahead of the state it reports; hMod passed as null, which returned a valid handle for a hook the system never called; and capture state in thread_local! when the callback does not run on the installing thread. After all three, most sessions still logged 0 keys seen.

Every symptom followed from keys never being recognised — unrecognised means not swallowed, so Ctrl+Alt+N reached the app's own registered hotkey and opened the overlay, and Alt+Z reached ShadowPlay. Shipped instead: the combination is typed. It reaches strictly more cases than the hook would have, including elevated-process conflicts UIPI hides from a normal-integrity hook. ADR-0003 is Rejected with the evidence; ADR-0004 records the decision.

What this cost, and why it is written down. Three build-and-test rounds, each needing a person at a physical keyboard, because none of it is observable from CI, from Linux, or over the dev link — a low-level hook needs an interactive desktop session and SSH lands in session 0. The instrumentation that finally separated "installed but never called" from "called and kept nothing" was a count of callback invocations, and it was added late. One diagnostic was logged at debug while the logger runs at info, so it never appeared at all. Prefer mechanisms whose correctness can be established off the target machine.

Settled, 2026-09-08

The hotkey was made fixed rather than configurable, and the last two defects closed. Verified at the Windows desktop against a release build.

The Windows hotkey is fixed at Ctrl+Alt+N Verified

Two mechanisms were built to let the settings field read a combination another application had claimed — a keyboard hook that never captured one, and a typed field that was never exercised. Rather than carry a third attempt into v1 for a setting no user has asked for, the combination is now fixed and choosing your own is deferred to #46, gated on the release. Registration is untouched: still a real RegisterHotKey call that names a genuine conflict, so #21's differentiator holds — what is deferred is acting on it by choosing another key. ADR-0005.

Close-to-tray applies without a restart Verified

close_to_tray was read once at launch and captured into the window-event closure, so toggling it did nothing until relaunch — the same read-once-at-startup shape as the hotkey registration bug. Now read when the close is requested, and the toggle no longer promises a restart. Still gated on a tray icon actually existing, which is built once in setup: hiding to a tray that is not there would leave the window unreachable, which is the failure #44 fixed from the other direction.

The overlay, the tray, and the settings panel Verified

Quick capture opens on Ctrl+Alt+N; the tray menu opens on right-click with a working Quit and the window restores on left-click; the hotkey section shows the binding read-only with no orphaned controls. Checked against the release build at 7f12749.

Found here, not fixed here

Surfaced by this pass, but none of it is #21's code. Recorded so the next person does not rediscover them from scratch.

Tray: a click cannot restore a destroyed main window — #44, fixed above

lib.rs, setup_tray. Both the tray handler and the single-instance callback re-show main only if let Some(window) = …get_webview_window("main"). With close-to-tray off, closing the window destroys it, so that is None and both paths silently do nothing — the app is running, invisible, and unreachable. Pre-existing; not in this diff.

Tray: right-click raises the window instead of opening the menu — #44, fixed above

lib.rs. The handler matches TrayIconEvent::Click { .. }, discarding the button field, so a right-click also shows and focuses the window — pre-empting the context menu. That makes Quit unreachable, which with close-to-tray on leaves no graceful way to exit at all. Pre-existing; not in this diff.

Close-to-tray needs a restart to take effect — fixed above

Observed 2026-09-07, fixed 2026-09-08. Kept here because it was found the same way as everything else in this section: by using the app rather than by testing it.

Autostart opens the full window at login

The Run value carries no quiet-start flag, so a login pops the main window even with a tray icon configured. Every neighbouring value in that same key uses one — -silent, --minimized, --startup_mode, --autostarted. Behaviour question, not a defect: item 4's criterion is "launches at login", which it does.

The capture window flashes white at launch

Fix 2 hides the window as soon as our code can, but Tauri has already shown it by then, so a brief white flash remains at startup. Cosmetic, and much better than the window staying up permanently, but not nothing. Worth a follow-up if it bothers anyone in daily use.

Release builds have no logs at all — #45, fixed above

lib.rs gates tauri_plugin_log behind cfg!(debug_assertions), so every diagnostic in this module is discarded in the shipped build — including the one explaining why a hotkey is unavailable. Three of the five defects above were only diagnosable after switching to a debug build. Pre-existing, and squarely at odds with the reasoning in startup.rs about reasons needing to be readable without a debugger.

Verification correction Fixed

GitHub verification initially failed because show_main_window carried the same #[cfg(desktop)] attribute twice. The redundant attribute was removed in 07c0004; it had no runtime effect.

Two maintainability observations Non-blocking

The Linux and Windows hotkey backends each publish status through the same state-lock-and-event sequence, and each reaches through configuration to answer whether an active vault exists. Extracting neutral helpers would reduce future duplication, but neither observation changes the verified behavior or blocks this feature. They remain review notes rather than expanding this already cross-platform PR.
