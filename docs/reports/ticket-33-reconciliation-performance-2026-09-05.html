Reconciling the index instead of rebuilding it

#33's acceptance criteria include a specific, measured performance claim: opening a large, unchanged vault must be faster than the full rebuild it replaces, with a figure recorded rather than asserted. This is that measurement, plus the correctness checks the same change needed.

All acceptance criteria pass. Reconciliation is ~6.3× faster than a full rebuild at both 5,000 and 20,000 notes, and the cost of reconciling is dominated by determining what changed, not by re-reading it — touching 20 of 20,000 notes cost 8 ms more than touching none.

What changed

Every document gains a fingerprint field — the note's file size and modification time, encoded as one opaque string, never queried or sorted on. Opening a vault now calls reconcile() instead of rebuild(): it walks the vault reading only filesystem metadata (no file content), reads every stored fingerprint back out of the index in one pass over the segment store (also no file content), and only for a path whose fingerprint differs — new, edited, or missing from one side — does the actual read-and-parse a changed note requires. An untouched vault does zero of those reads.

INDEX_SCHEMA_VERSION was bumped, so the first open after upgrading gets an empty index (the existing wipe-on-mismatch logic, unchanged). Reconciling against an empty index treats every on-disk note as new, which is exactly a rebuild — the one-time post-upgrade case needed no special-cased code path, only a test proving the general algorithm degrades to it correctly.

Reconciliation fails safe: any error walking the vault or reading the index falls back to a full rebuild(), the same pattern the incremental write paths already use. Only the desktop vault-open path changed. Mobile's index is RAM-only (rebuilt on every process start because there is nothing to persist between opens), so reconciliation has nothing to compare against there and mobile keeps calling rebuild() as before.

Performance

Measured directly against SearchIndex::rebuild and SearchIndex::reconcile on real on-disk indexes and synthetic vaults, each note ~120 words with realistic frontmatter. Both figures are a second call after an initial warm-up rebuild, so filesystem and page caches are equally warm for both.

Vault sizeFull rebuildReconcile, unchangedReconcile, 20 notes touchedSpeedup
5,000 notes (20 MB)126 ms20 ms—6.3×
20,000 notes (79 MB)406 ms65 ms73 ms6.2×

The ratio holds across a 4× change in vault size, consistent with both operations scaling with the number of notes — reconcile's saving is a smaller constant per note (a metadata stat and a string comparison, instead of a file read, a frontmatter parse, and tokenization), not a change in complexity class. The 20-touched-note run adds only 8 ms over the zero-change run at 20,000 notes, confirming that reconciling cost is dominated by deciding what changed rather than by re-indexing it.

Not measured: an actual application-startup wall-clock comparison, or a vault with the machine-local index cold (first access after boot, no page cache). The library-level timing here isolates the change this ticket makes; it does not include Tauri startup, vault-open plumbing, or disk-cache-cold I/O.
