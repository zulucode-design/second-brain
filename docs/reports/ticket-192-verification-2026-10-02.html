Ticket #192: unsaved edits on a note that changed on disk

2026-10-02, Fedora laptop. Issue: when the open note had unsaved edits and its file changed on disk (a sync run, a conflict choice), every later save failed with “Save conflict”, the app offered no reload, discard or merge, and the window could not close.

Design

Settled by Sol (gpt-6.1-sol, high effort) in two consult passes under Nicolas's delegation. Sol rejected the first proposal, which kept the draft in a copy and silently loaded the disk version, because it chose “take disk” for the user and let the close go ahead without a choice. The final design:

  • The editor saves through save_note_or_preserve. While the note on disk is still the revision the editor read, that is an ordinary save. Otherwise the draft goes durably to a Syncthing-style conflict copy beside the note, and the note is not touched. A missing note's folder is recreated for the copy only after the path is proven to stay inside the vault and outside its metadata.
  • While the conflict is unresolved, every save refreshes the same copy and never writes the note, even if the disk returns to the expected revision. The editor stays dirty, so a navigation or close is refused at once, with the dialog in place of the generic save alert. The 10 s close handshake never waits on the user.
  • The dialog offers Keep my edits (the copy replaces the note and the disk version goes to Trash), Take disk version (the copy goes to Trash), Compare, and Cancel. For a note that is gone, Close note leaves the copy in Settings › Sync › Conflicts. Cancel keeps a bar above the note, and an explicit save, navigation or close brings the dialog back.
  • A choice first proves the newest text is in the copy, flushing again when the first flush joined an older in-flight save. The editor is frozen while the choice is applied, and any change to the document or a draft ends it with nothing replaced.

Automated checks

pnpm verify passes on the fix commit: 197 node tests and 636 Rust tests, plus svelte-check, clippy and the build. New tests:

  • Rust (vault::operations): a save while the disk is unchanged; a changed note keeps the draft in one copy and refreshes it while unresolved, even when the disk returns to the expected revision; a removed copy is replaced by a new one; a note whose folder is gone; copies of other notes, paths outside the vault, metadata paths, non-Markdown paths and a symlinked folder are never written. Two guards were removed in turn to check that the tests fail without them.
  • Node (tests/disk-conflict.test.mjs), with the real SaveCoordinator: newer typing joined to an older preserving save reaches the copy before Keep, Take or Close; a failed save, an unexpected successful save, typing, a same-path reload, or a draft during the flush or the read ends the choice with nothing replaced; a failed resolve keeps the edits in a fresh copy; the generic alert is suppressed for the conflict; source checks for both windows' close paths and the editor wiring. Removing the newest-receipt check or the post-read guard fails them.
