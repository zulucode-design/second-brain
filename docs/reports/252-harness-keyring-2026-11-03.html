Issue 252: alpha harness keyring check verification

2026-11-03. The Gate 3 walkthrough in scripts/alpha-harness.mjs plants a synthetic OpenAI key, sk-alpha-harness-<uuid>, in the app's config.json, to prove that diagnostics redact it. The app moves that key into the OS keyring, into its one global ai:openai entry for service io.github.zulucodedesign.SecondBrain. The harness never saved what that entry held and never removed it. A walkthrough on a machine with a real OpenAI key saved in Second Brain would have overwritten the key, and every walkthrough left a fake one behind. The #237 installed checks did the same on both machines on 2026-11-02. No real key was lost, because Nicolas never saved one.

The branch makes the walkthrough refuse, and clean up after itself. Before a run changes either machine, it asks each machine's keyring whether an entry exists for each AI key the run will plant. It reads existence only. If one exists, the run stops and names the machine, account and service. If none exists, the run plants its key, and afterwards deletes the entry the app made from it, whether the run passed, failed or received Ctrl+C or SIGTERM. The trace records whether each entry existed before the run, whether it was removed and whether anything was left, and never a value.

Publication is pending. The branch is fix/252-harness-keyring. Candidate 56d5bf7a1437d5fa6622091fb40c66aba12434f0 passed the verification below on Fedora and Windows, apart from the one existing #244 test that fails Windows pnpm verify. That includes a refusal run and a passing two-machine Gate 3 run on real keyrings. Review round 7 was clean on both axes at d326b0b58c0da93ce5751b4993d95bb0653533c8, the head the candidate merges main into. The branch's five files are identical to it (see "Candidate and provenance"). No round is the final review. What the fix does

The check covers the accounts the run plants. Today that is ai:openai only, through the harness's PLANTED_AI_KEYS map, so the trace's entries object names that one account. The app's four AI accounts are ai:anthropic, ai:openai, ai:ollama and ai:openai-compatible. The Windows credential script accepts exactly those four targets and refuses every other. A check that plants another key adds one line to PLANTED_AI_KEYS, and the check, the re-check, the removal and the trace follow it. The verification below looked at all four accounts on both machines before and after the runs.

MachineHow existence is read, without reading a value
Fedora The Secret Service SearchItems method, called with busctl --user call org.freedesktop.secrets /org/freedesktop/secrets org.freedesktop.Secret.Service SearchItems and the attributes service and username. It answers with two lists of item paths, unlocked and locked, and never a secret. An entry exists when either list is not empty, so a locked entry counts as present. A failed call, or an answer of any other shape, stops the run and is never read as absent. Attempt 1 used secret-tool lookup. Review round 2 found that it exits 1 with no message both for no entry and for an entry it could not unlock, so a locked entry read as absent. Attempt 3 replaced it. Removal uses secret-tool clear with its standard output sent to the null device, and the same search afterwards decides whether anything is left.
Windows scripts/windows/alpha-desktop.ps1 runs in the desktop session, because an SSH logon has no Credential Manager, through the harness's scheduled-task path. It calls CredReadW for the target <account>.<service>. Only ERROR_NOT_FOUND (1168) means absent. Any other error stops the script, which then writes only the call name and the error code. CredDeleteW may succeed or fail with 1168, and nothing else. The script reads the credential before and after its work and writes two flags, found and left, to a result file named for that one call. An entry that either read saw counts as present, so found: false, left: true is present. The script overwrites the credential buffer before it frees it, and the controller passes on only the two flags.

Order of a walkthrough, as docs/alpha-harness.md now documents it:

  • The controller reads the candidate and harness commits and deploys the harness's own tools to the Windows test folder, because the Windows check runs from them. Then it checks both machines. This happens before the Fedora candidate install and before the Windows stale-run recovery. Attempt 1 checked after both, and review round 1 found that this changed the machines before refusing.
  • Immediately before a machine's config.json receives the key, the controller asks again and arms that machine's removal only if no entry exists. A launch between the first check and the plant can file a key from the copied config. If an entry appears, that machine stops with nothing planted and nothing deleted.
  • Once a machine's app and driver are stopped, the controller deletes the planted entry on every machine whose plant was armed, and checks that none is left. An entry left behind fails the run. A run that refused, or failed before the plant, deletes nothing. Each cleanup step runs even when an earlier one, a failure report or a trace write threw.
  • Ctrl+C and SIGTERM stop the walkthrough at its next step. The controller ends its WebDriver sessions, stops the app and driver by exact PID, waits for the gate to unwind, and then runs the same cleanup as a failed run. A run that received a signal never records run-complete and exits non-zero. A hard kill (SIGKILL, a closed terminal, a power loss, a cancelled GitHub Actions run) cannot clean up. The leftover entry makes the next run refuse and name it.
  • Trace events: ai-keys-checked (existed per account), ai-keys-armed (armed, existed), ai-keys-removed (armed, removed, left) and, after a signal, stopped-gate-settled. removed is true only when the entry existed at cleanup and was gone afterwards, so a true value shows that the plant produced an entry.

Changes from the issue text

  • Nicolas's decision of 2026-11-02 replaced the issue's first two criteria, which saved the previous value and restored it. The harness refuses instead, and removes what it planted. The third criterion changes with it. The trace records existed before, removed and left after, where the issue said "restored".
  • The documentation criterion is met by the subsection "AI keys in the OS keyring" in docs/alpha-harness.md, under Machine-state safety. It says that any one-off verification script that plants a key must check first, remove what it planted, check that nothing is left and keep every value out of its output. It also records the #237 failure.
  • The test criterion asked for the absent, present and fails-after-planting cases on both platforms' code paths. The new test file covers them against fakes of both keyrings, plus signals, locked entries, trace failures and the Windows result files and timeouts. See "Added tests matched to execution".
  • The branch is wider than the issue. After review round 3 Nicolas decided that Kiro fixes failures in teardown code that every gate shares and that predates this issue, and after round 4 he decided to keep fixing until the review came in clean. The branch therefore changes behavior for every gate:
    • finishMachine no longer throws, and a failure to write a teardown trace line is now an error the gate receives. A passing gate with an unwritable trace fails.
    • A failed stop step no longer skips later stop or restore steps. The Windows restore is attempted after a failed process stop, and the worker refuses it while installed processes remain.
    • The Windows worker's driver stop, finalize, recovery, damaged-copy move, artifact removal and forced stop each run every item on its own and keep the first error. Finalize keeps the run's lock and journal when any step failed, so the next run's recovery finishes the rest. Recovery now also moves a stale run's damaged config copies, and finalize removes the junction and tasks before it removes the lock.
    • Gate 1, the restore gate and the acceptance gate write their failure reports and teardown lines through a trace writer that never throws. A trace-only failure never replaces a real error. The restore and acceptance gates take an injectable I/O object, with defaults that make the same calls as before.
    • The DesktopScript action of scripts/windows/alpha-harness.ps1 (added to the allowed files in attempt 2) waits while a task is Queued or Running, counts only Ready and Disabled as finished, always tries to stop a task not known to be finished, and unregisters it only once it is confirmed stopped. Otherwise it leaves the task registered and the harness keeps that call's result file. Someone stops the task by hand before the next run.
