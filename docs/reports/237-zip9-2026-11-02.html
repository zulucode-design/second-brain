Issue 237: zip 9 verification

2026-11-02. The branch moves the zip crate from 2.6.1 to 9. The manifest asks for "9" and the lockfile resolves 9.1.0, where the issue text names 9.0.5. In src-tauri/src/backup.rs a restore now reads every entry name with zip 9's fallible name() and no longer calls zip's enclosed_name(). A new function, native_entry, reads each name with the operating system's own path rules, and extract_and_validate_with writes exactly the paths its first pass accepted. On Windows a helper, windows_unsafe_component, repeats the refusals zip 9.1.0 makes there, with a device-name check that cannot panic on names such as naïve.md. The backup writer gains one call, .system(zip::System::Unix), so a backup written on Windows keeps the header fields earlier releases wrote. diagnostic_export.rs changes one test line.

Publication is pending, and the verification run failed its own cleanup. Every application check the issue asks for passed on candidate 8f54c08 on Fedora and Windows, apart from the one existing #244 test that fails Windows pnpm verify. The cleanup did not pass. Sol's installed-check script planted a synthetic OpenAI key in the app's config on both machines. The app moved that key into the OS keyring and overwrote the app's global OpenAI entry, ai:openai for io.github.zulucodedesign.SecondBrain, and nobody had saved the previous value. Both machines still hold the synthetic value. Nicolas confirmed he never saved a real OpenAI key in Second Brain, so no real key was lost. Deleting the two entries waits for his approval. Final review of the publication head, the PR, CI and his merge approval have not happened.

Changes from the issue text

  • Criterion 3 said to refuse a\b.md on Linux and to keep enclosed_name() as the gate. Round 1 Standards review found that this refusal makes a whole Fedora backup unrestorable whenever the vault holds a file with a literal backslash in its name, because v0.1.0-alpha.1 and this build both write such a name unchanged. Nicolas approved revising criterion 3 on 2026-10-25, so that safe Fedora names with backslashes survive while the traversal, root, drive and symlink refusals stay. Attempts 2 to 4 follow that revision.
  • Restore no longer calls enclosed_name() anywhere. Native path validation decides every name. Kiro's attempt-4 handoff lists what differs from zip's own Windows check. A name such as COMı.md, with a dotless i, is accepted, where zip refused it through a lossy byte cast. COM0 and LPT0 are not refused, as before. Windows case-only collisions and 8.3 short names are not refused either.
  • The writer change is a fix for zip 9, not a format change. zip 2 marked every entry as made on Unix. zip 9 marks entries as made by DOS on Windows unless told. Names, separators, directory entries and Deflated level 6 are unchanged.
  • Known limitation, recorded as Nicolas directed on 2026-10-26. v0.1.0-alpha.1, built with zip 2.4.2, reads an entry whose name ends in a backslash as a directory. A regular file such as Projects/ends in\ on Fedora therefore comes back from alpha.1 as an empty folder, even from alpha.1's own backups. This build restores it as the file, from old and new backups. Windows cannot hold such a name. The issue text says the app's sanitize_filename turns a backslash in a note name into -, so only a file added by hand can carry the name. The ledger records that no separate implementation issue was opened.

Why Windows runs 39 backup tests and Fedora 42

backup.rs holds 43 #[test] functions. Four carry #[cfg(unix)] and one carries #[cfg(windows)], so Fedora builds 43 - 1 = 42 and Windows builds 43 - 4 = 39. The Fedora-only tests are fedora_backslash_names_survive_a_backup_and_restore, a_whole_vault_opens_even_when_cleanup_cannot_finish, edits_made_after_a_kept_restore_survive_the_delayed_cleanup and edits_made_after_an_undone_restore_survive_the_delayed_cleanup. The Windows-only test is a_locked_entry_exhausts_the_retries_and_refuses_to_open. Comparing the two backup:: logs name by name gives exactly those five differences.

The test-matching record, 237-vi-test-match.json, explains only the first one. It lists tests this branch adds or changes, and marks fedora_backslash_names_survive_a_backup_and_restore as not applicable on Windows. The other three Unix tests and the Windows test already exist on origin/main with the same gates, so I derived their part from the logs and the source. The same gating accounts for the full Rust totals. Fedora has 46 passing tests that Windows lacks, among them autostart, hotkey portal, symlink and permission tests, and Windows has 15 that Fedora lacks, so 768 - 31 = 737.

Cleanup failure: the OpenAI keyring entry

This is a failure of the verification run, not of the application. Sol's installed-check controller patched config.json on each machine to hold a synthetic OpenAI key, so that the diagnostics check could prove the export redacts it. On startup the app moves a plaintext key from config.json into the OS keyring and redacts the file. The script restored config.json, as the hashes below show, but the keyring entry is not part of what it restored. The key went into the app's global entry, ai:openai for service io.github.zulucodedesign.SecondBrain, which holds one OpenAI key for the whole app. That overwrote whatever the entry held, and the script never saved the previous value.

  • Fedora. The Secret Service entry existed before the run. Its attributes show created = 2026-09-23 12:22:34 and modified = 2026-11-02 17:01:41, and the modified time matches the start of the Fedora installed run at 17:01 UTC. The audit, 237-vi-keyring-audit-fedora.json, found the entry and found that its value starts with this script's synthetic prefix. The previous value is gone.
  • Windows. The Credential Manager entry for the same account was last written at 2026-11-02T17:00:20Z, during the second Windows run, and its value starts with the same synthetic prefix (237-vi-keyring-audit-windows.log). No record says whether the entry existed before the run, and no pre-run snapshot was taken, so what it held is unknown. The saved original config.json had no plaintext OpenAI key.
  • No copy of a previous value exists. Sol searched the configuration, state and saved-original JSON files in its own and the harness's working folders for any non-empty openai_api_key and found none (237-vi-prior-key-sources.json is an empty list).
  • The key is a synthetic value, and no real key was lost. Nicolas confirmed he never saved a real OpenAI key in Second Brain. This report prints no key value, and its author did not read the keyring.

The standard Gate 3 walkthrough does the same thing. scripts/alpha-harness.mjs, around line 1865, creates sk-alpha-harness-<uuid>, patches it into config.json as openai_api_key and records config-patched. Its cleanup restores config.json and clears only the Notion credential. It never clears or restores the OpenAI entry. The plant arrived in commit b9dde9d on 2026-09-22, and the Fedora entry's creation date is the next day. No committed walkthrough trace covers 2026-09-23, so nothing here proves that a walkthrough created the entry. The 15 committed walkthrough traces in docs/reports/evidence/, dated 2026-09-26 to 2026-10-24, show the plant on Fedora in 12, on Windows in 12 and on both in 10. Fourteen of the 15 show it on at least one machine. The other, 20261003T005823Z, is 3 rows long and ends before any plant.
