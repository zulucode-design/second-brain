Issue #14 — pre-sync restore fix and manual verification

2026-09-29. Candidate 96a3e5b could not restore a pre-sync backup through the installed Fedora Backup UI: Restore commit failed and was rolled back: .stfolder already exists (evidence event fedora-presync-restore-failed in prealpha-post162-96a3e5b.jsonl). Nicolas classified it P1, blocking the alpha. This report records the cause, the fix, and the check in the real app. It covers the first of two #14 pull requests; the second covers backups only before incoming changes and retention. The installed proofs follow once both have merged (corrected 2026-09-29; this said the second pull request covered them).

Cause

The evidence note suspected plan_commit. The fault was in the backup. The walk in create_backup_with_prefix (now create_backup_of_kind) skipped hidden entries with continue. For a directory that skips only the directory entry and never its children. Syncthing keeps a marker file in every synced folder's .stfolder, so every pre-sync ZIP carried .stfolder/syncthing-folder-687dd2.txt. The same leak took in every entry not named with a leading dot inside a .git, .obsidian, or .stversions folder. The restore staged .stfolder, but a restore never moves live top-level dot entries aside. The publish therefore met the live .stfolder and rolled back. Any vault with a top-level dot folder containing an entry whose name does not start with a dot, synced or not, failed the same way.

Fix

PartChange
Backup contents A backup now holds exactly what a restore replaces: every top-level visible entry with its whole subtree, nested dot entries included, and .helixnotes. Other top-level dot entries stay out. Before this, nested dot files were left out, so a restore silently deleted them along with the folder they were in.
Restore of older archives plan_commit never publishes a top-level staged dot entry. Archives made before the fix restore, and their dot folders are removed with the stage.
Backup list Each listed archive carries a kind (backup or preSync), set in Rust from its filename prefix, and Settings > Backup labels it Backup or Before sync. list_backups now dates pre-sync archives from their names, as it already did for scheduled ones.

Two new tests and one rewritten test fail against main (one of them does not compile there, because BackupKind is new) and pass with the fix. The rewritten test, formerly a_dot_folder_in_both_vault_and_backup_survives_a_failed_restore, expected such a restore to fail cleanly; as dot_folders_in_an_old_archive_leave_the_live_ones_untouched it restores an old-style archive into a vault with a live .stfolder, and on main it fails with the production error. One new test checks that a backup's names are exactly what a restore replaces, and that a round trip restores the vault byte for byte. The other checks that both archive kinds are dated from their names and carry their kind.

Manual verification (Fedora 44, release build, isolated XDG directories)

A copy of the failing run's isolated profile and vault (~/sb88/runs/i14-restore-check) was opened with the release binary from commit 7d998b3, which includes the first round of review fixes (later commits change only comments, a constant list of the same two kinds, and report prose), driven by tauri-driver with XDG_CONFIG_HOME and XDG_DATA_HOME inside that copy. Sync was disabled with no peer, so nothing was sent to the other machine. The archive was the one that failed: helixnotes-pre-sync-2026-09-29T03-25-00.zip.
