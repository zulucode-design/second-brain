Issue #174 — harness runs leave the real Windows logs and WebView2 data alone

2026-09-30. Every launch of the installed app writes two folders in the real %LOCALAPPDATA%\io.github.zulucodedesign.SecondBrain profile that no harness step redirected. logs gains lines, and WebView2 writes its cache and storage to EBWebView. After #167 these were the only parts of the real profile that a run changed.

Decision

The issue asked whether to redirect the folders or only record what a run added. They are redirected. A run's log lines are evidence, so they belong in the run directory, and an append-only log cannot be cleanly put back afterwards. The user's WebView2 data stays exactly as it was, so no question remains about a later launch noticing it.

Fix

StepChange in scripts/alpha-harness.mjs
prepare The run's journal names each folder, its target runs\<run>\windows\profile\<name>, and an aside path in io.github.zulucodedesign.SecondBrain.alpha-harness-<run>. The aside folder sits beside the profile, not inside it, so an uninstall that clears app data cannot reach the user's folders. Both folders are checked before the lock is written: one that is already a link, or an aside path that already exists, fails the run with no lock left behind. After the lock is written, each folder is renamed aside and a junction to the target replaces it.
recover and finalize restoreProfileFolders is idempotent, so it can finish a run stopped at any point. It removes a junction only if the junction points at this run's target, and it removes it with rmdir, which never touches the target. It then renames the user's folder back and removes the aside directory only once it is empty. A path it cannot inspect, for example because access is denied, fails the restore and keeps the lock, rather than passing for absent. Nothing is copied or deleted.
desktop The toast count still reads %LOCALAPPDATA%\…\logs, which now leads into the run's own logs.
